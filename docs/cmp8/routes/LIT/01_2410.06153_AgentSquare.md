## 我的收获

### 一、★★ 这篇重新定义了我们的任务 —— 我们缺的不是"优化器"，是"模块化的设计空间"

论文提出的问题叫 **MoLAS（Modularized LLM Agent Search）**：
把 agent 设计写成**四个模块的元组**，每个模块有**统一的 IO 接口**：

> **A = (P, R, T, M)**，P∈Planning池，R∈Reasoning池，T∈ToolUse池，M∈Memory池
> 目标：给定任务描述 d 与任务级评估函数 R₀，**最大化 R(A)**（Eq.1）

四个模块的接口（逐字要点）：

| 模块 | 输入 | 输出 | 功能 |
|---|---|---|---|
| **Planning** | 任务（+可选反馈） | 子任务 | 拆解为子目标 |
| **Reasoning** | 子任务 | 解 | 解子任务（CoT / ToT 等）|
| **Tool Use** | 子任务 | 工具选择 | 从工具池里选 |
| **Memory** | 观测 / 动作 | 记忆状态 | 写入与检索 |

⇒ ★★★ **映射到我们**：我们的三条路线其实**已经天然对应这四个槽位**，只是从来没有形式化：

| AgentSquare | 我们的对应 | 我们现在有吗 |
|---|---|---|
| **Planning** | 拓扑选择（T0–T5 模板）| ⚠️ 有 6 个，但**是手写枚举，不是模块池** |
| **Reasoning** | 断言抽取 / 拆分 / 去冗余 / 条件重采样 | ✅ 路线 A、C 里都有 |
| **Tool Use** | 依据包核验（唯一接触 oracle 的阶段）| ✅ 都有 |
| **Memory** | 断言池 / 维度卡片库 / 结论空间 `C_t` | ⚠️ A 有断言池、C 有卡片，但**没有跨臂共享的卡片库** |

⇒ ⇒ **所以"我们没有优化策略"这个诊断是不完整的。**
更准确的诊断是：**我们有三条手写的点（A/B/C），而不是一个可以搜索的空间。**
**先模块化，才有搜索空间；先有搜索空间，优化策略才有对象。**

⇒ ★ 而且论文给"模块化"的三条理由，**每一条对我们都成立**：
- **可复用**：Chain-of-Thought ↔ Reasoning、Self-refine ↔ Reasoning、ToT ↔ Reasoning、DiLu ↔ Memory……
  ⇒ **我们路线 C 的 12 个参数里有相当一部分就是"某个模块的实现细节"**
- **可扩展**：新模块发布进池子 ⇒ **我们路线 C 的"拓扑菜单"应该是一个可增补的池，而不是冻结的清单**
- **可搜索**：统一 IO 接口（**代码与提示词两种形式都统一**）⇒ 可自动互换 ⇒ AutoML 式搜索

### 二、★★ 统一 IO 接口**顺手把我们的 L1 信用分配变成了结构保证**

我们的优化器契约 L1 写的是"消融式 Δ(component)"，我当时以为这需要额外工程。
⇒ **AgentSquare 的模块化让消融天然成立**：换一个模块 = 一次消融，因为接口统一、其余不变。

⇒ ★★ 而且他们的 baseline 名单里**就有我们路线 A 的组件来源**：
**12 个人工设计 agent**（CoT、Self-refine、ToT、Step-back、Voyager、HuggingGPT、Generative Agents、DEPS、OPENAGI、DiLu…）
⇒ ⇒ **我们的"承载面清单"可以直接对标他们的模块池** ⇒ 我们可以在他们的模块池上做**我们题域下的重搜**，
而不用从零发明可插拔的组件。

### 三、★ 它的"性能预测器"正是我们缺的那个"便宜预筛器"，而且我们的版本可以更便宜

它用一个 **in-context surrogate model**：把过去的 (agent, performance) 对塞进上下文，让 LLM **预测**候选配置的表现，
好跳过不promising的设计。实测：**与真实奖励的 Pearson ≥ 0.3**（各 benchmark），
在 ALFWorld 上把评估成本降到**全量跑的 0.025%**。

⇒ ⇒ **我们的成本结构（生成贵、测量免费）让我们可以做得更好**：
我们的预筛器**根本不需要 LLM** —— 先用**零调用启发式**淘汰：
操作分布熵、断言池大小、是否触发 fallback、`D` 的快速上界 ⇒ 只有存活的候选才花完整测量。
⇒ ★ 这条直接落到我优化器契约的"L0-2 重复测量"之前，作为**第 0 级筛选**。

### 四、★ 它给我们的"迭代预算"一个量级参照：10–20 轮

原文："most tasks converge within **10–20 iterations**"。
⇒ 我们契约里的 **K（改动预算）** 我当时按 8 写 ⇒ **偏小** ⇒ ★ 改成 **10–20**，且按臂对齐（对齐 2608.04341 说的"agent 数↔总提交数"混淆）。

### 五、★★ 它的"可解释设计洞见"给我们的"哪个组件带来了宽度"提供了可操作的产出形态

搜索结束后它能给出**人可读的模块配方**，例如：
- **ALFWorld**：`TD`（树分解）做 Planning + **`SF-ToT`（自反馈 + ToT）** 做 Reasoning + Generative Agents 的情节记忆做 Memory
  ⇒ **这套组合比单独的 Self-refine 高 25% 以上**
- **WebShop**：`IO`（迭代优化）做 Planning + `HTSS`（分层分类搜索）做 Reasoning

⇒ ★ 而且它报了一条**跨任务的规律**：
> **"对开放世界或组合型任务，planning 与 reasoning 模块通常是性能瓶颈；而复杂的 memory 模块主要在长程、具身场景才是关键。"**

⇒ ⇒ 对我们：**"哪个模块贡献了有效维度"这个问题，答案很可能不是"加更多承载面"（那是 Reasoning 侧），而是"拓扑/阶段划分"（Planning 侧）** ——
而这**恰好就是我们路线 A 复核 F3 暴露的那个洞**（路线 A 说"固定拓扑"却实现了一个数据依赖开关）。

⇒ ⇒ ★ **所以我们的 L1 消融应该优先做 Planning 侧的消融**（拓扑 vs 参数），而不是在参数里打转。

### 六、★ "混合优越性"这个观察，对我们 A/B/C 三路线的定位有直接含义

论文发现：**最好的 agent 常常是"人设计的 memory 模块 + 机器搜出来的 reasoning 模块"的组合**。

⇒ ⇒ **这直接支持我们路线 C 的核心命题**（人定结构 + 机器调数值）——
⇒ ★ **而且给了它一个独立的第三方证据**（不是我们自己说的）。
⇒ ⇒ 也说明**路线 A 与路线 C 不是互斥的**：A 的价值可能不是"当答案"，而是**提供一个高质量的 memory/装配模块**给 C 用。

### 八、★★★ 它有一条和 2608.04341 **同源**的统计硬伤 —— 我们必须躲开同一个坑

> **"没有报告 seed 数、没有报告重复次数、没有置信区间"**；公开代码里 `run_benchmark(agent, n=50)`
> ⇒ **报的是 best-of-50 的单点读数。**

⇒ 与 2608.04341 的评审意见（**"best-of-n 的最大值随 n 增大而偏高"**）**是同一个病**：
**两个"架构搜索"论文都在用 best-of-N 的单点读数比较，而 N 的差异与架构质量混在一起。**

⇒ ★★★ **这是这批文献给我最重要的一条横向发现**：
**我们要做的实验，恰好是这个领域最容易被这个坑吞掉的那种**
（我们本来就要跑多条路线 × 多次重复 × 取最好）。
⇒ ⇒ **我们的对策必须写进协议**：
① **重复次数 R 事前固定**（不由"跑够为止"决定）；
② **主读数取中位数**（不取最大值；best-of-N 只作**上界参考**并单独标注）；
③ **报噪声地板 δ**（同配置不同 seed 的读数波动），**增益必须 > δ 才算数**；
④ **跨臂对齐 R 与总调用预算**（否则"多搜了"会被读成"搜得更好"）。

⇒ 而 **AgentSquare 的消融表**给了我们一个正面范例：
**"w/o module evolution" 是一个单模块消融 ⇒ 模块级的贡献是可分离的**
⇒ ⇒ 这正是我们 L1（消融式信用分配）要的东西，而且它证明**在模块级做消融是可行且被同行接受的**。

### 九、它的"混合优越性"给了我们路线 C 一个第三方证据
最好的 agent 常是**"人设计的 memory 模块 + 机器搜出来的 reasoning 模块"**的组合
⇒ ⇒ **独立支持**了我们路线 C 的核心命题（人定结构 + 机器调数值）。

### 十、⚠️ 它的局限对我们同样是警告

论文自认：四模块**可能覆盖不了**多智能体系统与"内部世界模型"；**搜索质量依赖提议者 LLM**（用的是 GPT-4o）。

⇒ 对我们：
- ⇒ 我们的"提议者"是 MiniMax-M3.1-Flash-Preview ⇒ **提议者能力上限会直接压住搜索质量**
  ⇒ ★ 这和路线 C 复核 F7 抓到的"判官崩了"是同一类风险：**关键环节的模型能力必须单独体检**
- ⇒ 四模块确实不够 ⇒ **我们的"维度卡片 / 结论空间 / 承重检验"这一层，在 AgentSquare 的框架里没有对应槽位**
  ⇒ ⇒ ★ **这暴露了我们项目的一个真问题**：我们的架构里有一整层（**"哪些信息是承重的"**）是**评估侧**的，
  它既不在 Planning 也不在 Reasoning 里 ⇒ **它没有地方安放**
  ⇒ ⇒ 而这层恰恰是**我们的核心创新点**（思维面 = 有效信息维度数）
  ⇒ ⇒ ★ **所以模块化时必须加第五个模块**，或者把"承重检验"归入 Memory（因为它是"记住哪些信息承重"）。
  ⇒ ⇒ 我倾向**加第五个槽位**：`E (Evidence/承重)` —— 因为它有**独立的 IO**（输入候选断言+`C_t`，输出承重判定+支持的关系）
  ⇒ ⇒ ★ 这是一条**只有我们这个项目才有的模块**，也正是我们的差异化所在。

## 一句话
> AgentSquare 告诉我们：**"Agent 自主探索架构"的可搜索对象是"模块元组"，不是"整条流水线"。**
> 我们的 A/B/C 只是三个手写的点 ⇒ **先按 Planning / Reasoning / Tool Use / Memory（+ 我们独有的第五槽：承重检验）拆出统一 IO 接口，
> 再把三路线变成模块池里的条目，优化策略才有对象、消融才有结构保证、信用分配才可测。**
> 可直接抄的四条：① **统一 IO 接口 + 模块池**（把"路线"改成"模块组合"）
> ② **性能预测器做预筛**（我们可用零调用启发式，比他们更便宜）
> ③ **迭代预算 10–20 轮**（我们 K=8 偏小）
> ④ **"人设计 memory + 机器搜 reasoning"的混合优越性** ⇒ 给我们的路线 C 提供了第三方证据。
> 一条自省：我们的"承重检验"这一层**在四模块框架里无处安放** ⇒ 必须显式加第五个模块，
> 而这恰恰是我们唯一的差异化资产。
