## 1. 核心机制（具体到能照着实现）

| 项 | 内容 |
|---|---|
| **输入** | 任务（由自动课程提出）+ **智能体当前状态**：背包物品字典、装备、附近方块（32 格内）、近期见过的其他方块、附近实体（32 格内）、见到的箱子（未开 = "Unknown"）、生物群系、时间（sunrise/day/noon/sunset/night/midnight）、血量与饥饿（上限 20）、3D 坐标 (x,y,z) |
| **状态表示** | ★ **三个可分离的状态容器**：<br>① **技能库** = 一组 **JavaScript 程序**（每个程序 = 一个技能），**用"描述的 embedding"做索引**（`text-embedding-ada-002`）<br>② **课程上下文** = GPT-3.5 自问自答的问答对（可从 MineDojo wiki 检索文档）<br>③ **本轮上下文** = 上一轮生成的代码 + 环境反馈（chat log）+ 执行错误 + 自验证批评 + 当前状态 + 课程任务 + CoT 提示 |
| **动作/算子** | ① **课程器**（GPT-4，temp=0.1）→ 提出下一个目标；② **代码生成器**（GPT-4，temp=0）→ 生成可执行 JS；③ **技能管理器** → 检索（embedding top-k）相关技能并写入新技能；④ **自验证 critic**（GPT-4）→ 判成功 / 给批评；⑤ **控制原语**（人写的 API，共 8 个 + 大量 Mineflayer API）：`exploreUntil` / `mineBlock` / `craftItem` / `placeItem` / `smeltItem` / `killMob` / `getItemFromChest` / `depositItemIntoChest` |
| **过程/回路** | ★ **三层嵌套**：<br>**外层（终身）**：课程器给目标 → 智能体解 → 自验证确认 → 技能入库 → 课程器给下一个目标（循环到 160 次 prompting iteration）<br>**中层（技能）**：代码生成 → 执行 → 拿反馈 → 重新生成，**最多 4 轮**<br>**内层（课程）**：课程 prompt 里含"已完成任务"和"失败任务"两个列表 ⇒ **失败任务会被重提**<br>**停止条件（三个，都有）**：<br>· 单个任务：**自验证通过** ⇒ 入库并换目标<br>· 单个任务：**4 轮代码生成后仍卡住** ⇒ 放弃，向课程器要新任务<br>· 全局：**160 次 prompting iteration** 上限 |
| **输出** | **一个持续增长的技能库**（可执行程序）+ 探索轨迹 + 发现的物品清单。**最终交付物 = 技能库**（不是单条答案） |
| **谁来评价** | ★ **混合，但主信号是同源自评**：<br>· **自验证 critic = 另一个 GPT-4 实例**（同家族、可能是同模型）⇒ **同源自评**（我们坑 ⑥）<br>· **环境反馈 = 外部**（`bot.chat()` 报告缺什么材料、解释器错误）<br>· **课程器 = 外部 oracle 的一种**（任务达成与否由课程器下一步是否给更难任务间接体现）<br>**信号怎么回传**：critic 的"通过/失败 + 批评"**以自然语言形式直接进下一轮 prompt**（无梯度、无参数更新）——与 Reflexion 同构 |

## 2. 关键数字

**实验设置**
- 模型：`gpt-4-0314`（主）+ `gpt-3.5-turbo-0301`（课程上下文用 GPT-3.5，**因为预算**）+ `text-embedding-ada-002`（技能索引）
- 温度：**全部 0**，**唯独自动课程 temp = 0.1**（"to encourage task diversity"）
- 环境：MineDojo + Mineflayer JS；Cross 模拟等；**每个方法 3 次独立试验**（Trial 1/2/3）
- 对照：**ReAct / Reflexion / AutoGPT**（都重新实现为能在 MineDojo 里跑的形式），任务统一为 "explore the world and get as many items as possible"

**主指标与读数（正文逐字给出的数值）**
| 指标 | 读数 |
|---|---|
| 唯一物品数 | **63 个唯一物品 / 160 次 prompting iteration**，**是基线的 3.3×** |
| 科技树（Cross Maze 迭代数，越快越好） | 木质 **15.3×** 更快、石质 **8.5×** 更快、铁质 **6.4×** 更快；**钻石级只有 Voyager 解锁**（基线 GPT-4 = 7.5% → Voyager 15.0%，见文件 13 用的 LeetcodeHard 对照：Reflexion 15.0 vs GPT-4 7.5） |
| 地图穿越 | **2.3×** 更远 |
| 零样本泛化（新世界、未见过的任务） | Voyager **全部任务都解出**；**基线在 50 次 prompting iteration 内一个都解不出**。且**技能库还能反过来帮 AutoGPT 涨分**（"the skill library serves as a versatile tool that can be readily employed by other methods, effectively acting as a plug-and-play asset"） |
| 技能检索准确率 | **top-5 = 96.5%**，共 **309 个样本**（注：top-5 的技能会被放进 prompt） |

**消融（★ 全部是"去掉某个模块，看发现物品数掉多少"）**
| 去掉的东西 | 效果 |
|---|---|
| **自动课程 → 换成随机课程** | 发现物品数 **掉 93%**（"certain tasks may be too challenging if attempted out of order"）。手工设计的课程**也不如自动课程** |
| **去掉技能库** | 后期**明显进入平台期**（"tendency to plateau in the later stages"） |
| **去掉自验证** | 发现物品数 **−73%**（"**Self-verification is the most important among all the feedback types**"） |
| **GPT-4 → GPT-3.5（代码生成）** | 唯一物品数 **5.7× 更少** |
| 去掉环境反馈 / 去掉执行错误 | 正文只说"对探索有影响"，**未给数值**（图表在缺失的 figures/ 里） |

**成本**
- 无美元数字。⚠️ 但明确说：**"The GPT-4 API incurs significant costs. It is 15× more expensive than GPT-3.5."**
- 规模：**160 次 prompting iteration**，每任务最多 **4 轮**代码生成

## 3. ★ 它的「成功标准」是什么

**怎么判定自己成功了**
1. **主判据 = 外部环境真值**（发现多少唯一物品、地图覆盖多广、科技树推到哪一级）——**不是自评**
2. **对照 = 同任务同环境的 ReAct / Reflexion / AutoGPT**
3. **判据可数**（63 个物品、top-5 检索 96.5%、3 次试验）
4. ⚠️ **但内部循环的判据是同源自评**（critic）

**否证/失败条件**
- ✅ **有**：**"w/o Self-Verification"** 是一个明确的负向条件（−73%）；**"w/o Skill Library"** 明确说"后期平台期"
- ✅ **有**：论文在 Limitations 里自认 critic 会失灵（见 §4）
- ✅ **有**：**"Voyager w/o skill library exhibits a tendency to plateau in the later stages"** —— 这是"停在局部最优"的准确实例
- ⚠️ **"不可分辨"**：❌ **没有**。3 次试验、无方差、无 CI、无噪声地板。**"3.3×" 这类读数的可信度没有任何统计支撑**。

**★ 一个必须点出的判据污染**
**自验证 critic 既是"内部回路的停止条件"，又是"最重要的组件（−73%）"** ⇒ **整条流水线的成败压在一个同源 LLM critic 上**。这正是我们坑 ⑥（自评污染）的教科书形态：
> 若 critic 判错了，Voyager 就会 (a) 提前入库一个坏技能（污染技能库 ⇒ 后续检索会把它当有用技能取回来），或 (b) 拒收一个好技能（浪费）。**两种错误都会被后续步骤放大。**
论文自己承认："Occasionally, self-verification module may also fail, such as not recognizing spider string as a success signal of beating a spider."（**给了具体例子：把蜘蛛丝当成打蜘蛛成功的信号**）

## 4. 自认的局限（原文优先，逐字）

§Limitations 全文三小节：
1. **Cost**：
   > "The GPT-4 API incurs significant costs. It is 15× more expensive than GPT-3.5. Nevertheless, Voyager requires the quantum leap in code generation quality from GPT-4 (Fig. ablation), which GPT-3.5 and open-source LLMs cannot provide."
2. **Inaccuracies**：
   > "Despite the iterative prompting mechanism, there are still cases where the agent gets stuck and fails to generate the correct skill. The automatic curriculum has the flexibility to reattempt this task at a later time. **Occasionally, self-verification module may also fail, such as not recognizing spider string as a success signal of beating a spider.**"
3. **Hallucinations**：
   > "The automatic curriculum occasionally proposes unachievable tasks. For example, it may ask the agent to craft a 'copper sword' or 'copper chestplate', which are items that do not exist within the game. Hallucinations also occur during the code generation process. For instance, GPT-4 tends to use cobblestone as a fuel input, despite being an invalid fuel source in the game. Additionally, it may call functions absent in the provided control primitive APIs, leading to code execution errors."

另有关键的自认式表述（§Method 末）：
   > "**However, LLMs struggle to produce the correct action code consistently in one shot.**"（⇒ 迭代提示的存在理由）
§Experiment 里对基线的自认式加限定：
   > "Because there is no LLM-based agents that work out of the box for Minecraft, we make our best effort to select a number of representative algorithms as baselines. These methods are originally designed only for NLP tasks without embodiment, therefore we have to **re-interpret them to be executable in MineDojo** and compatible with our experimental setting"

## 5. ★ 对我们项目的可迁移点

### 5.1 ★★★ 抄「**"目标"与"程序"分离，且目标由一个独立的课程器产生**」
Voyager 的三件套里，**最可迁移的不是技能库，是"自动课程"**：
- 课程器看的是**当前状态 + 已完成/已失败任务列表**，产出**下一个目标**
- 目标**不规定解法**，只规定"要去哪"
⇒ **这是我们路线 A（固定拓扑）里"目标生成"这一步的现成形态**：
  - 我们的"依据包" ≈ 课程器读的状态
  - 我们的"建议 op" ≈ 课程器给的目标
  - ⭐ **关键：课程器不写"你应该想到哪几点"** ⇒ 与文件 18 的 S4 Fig 结论一致（"只奖励探索，技能作为副产品出现"）
- ⇒ **省掉什么实验**：我们的"反思/建议"环节如果规定得太细，会退化成"照着清单填"。**把"目标生成"和"求解"分成两次调用、且目标不泄露结构**，是一个能抄的最小改法。

### 5.2 ★★★ 抄「**"已失败任务列表"作为状态的一部分**」
课程 prompt 里显式包含 **previously completed and failed tasks**。
⇒ 这是一个**"失败历史"即状态**的现成设计。
- **省掉什么实验**：我们不需要额外设计"记忆结构"；**"失败任务列表"是最低配的记忆形态**（一个可数的列表，而不是自由文本记忆）。
- ⭐ **对我们的直接价值**：我们的"净维度增益"如果只在**成功样本**上测，就会漏掉"失败样本上多出的维度是不是花絮"这一类失败模式。⇒ 把**失败样本的维度数**单列成一个读数。
- ⚠️ **但要小心坑 ⑦**：课程 prompt 的措辞是**中性的**（"previously completed and failed tasks"），不是"你上次错了"。⇒ 这正好是我们要的**措辞中性**范例。

### 5.3 ★★ 抄「**"技能库 = 可复用程序 + embedding 索引"**」
技能被**程序化**（不是自然语言描述），并用**描述的 embedding** 检索。
⇒ 我们的"结构化状态"（可被检索、可被组合）可以照抄这个形态：
- 状态条目 = **结构化对象**（不是自由文本）
- 检索键 = **描述的 embedding**（检索用 embedding 没问题；⚠️ **只有"新颖/冗余"判据不能用 embedding**——这正是我们 embo-01 的坑）
- ⇒ **这个区分很重要**：Voyager 用 embedding 做**检索**（相似 ⇒ 取用），**没有**用 embedding 做**新颖/冗余判据**。⇒ 我们的路线 A 若要做"技能库/依据库检索"，embedding 是安全的；但**维度计数与去冗余必须走结构**。

### 5.4 ★★ 抄「**"自验证是最重要组件"这个反直觉结论，以及它的警告**」
−73% ⇒ **在没有外部信号的地方，判官就是全部**。
⇒ **对我们的含义（双向）**：
- **坏的一面**：我们不能把"判官说更好"当结论（坑 ⑥ + 坑 ④ 叠加）
- **好的一面**：它证明了"判官"这个位置**必须存在**，而且它的质量**直接决定整条流水线的成败** ⇒ ⇒ **我们的 L0（目标可重复性）不是可选项，是生死线**。Voyager 的 −73% 就是"L0 不过关 ⇒ 后面全白做"的外部证据。
- ⇒ **省掉什么实验**：我们不需要再论证"为什么要先把目标做到可重复"，可以直接引用"自验证去掉 = −73%"来支持 **L0 是准入券**（OPTIMIZER-CONTRACT §1.3）。

### 5.5 ★★ 抄「**技能库可被别的方法即插即用**」
"our skill library … gives a boost to AutoGPT … effectively acting as a plug-and-play asset to enhance performance."
⇒ **路线 A 的产物应该是"可被路线 B/C 复用的资产"，而不是"某个臂的私有优势"**。
⇒ ⇒ 我们的路线 A 若设计出"结构化状态生成器"，它应该能被路线 B（训练架构）当**特征/监督信号**用。⇒ **这条可以直接写进路线 C 的设计：先设计出 A 的产物接口，再让 B 去学怎么生成它。**

### 5.6 ★ 抄「**多轮重试上限（4 轮）+ 换目标**」
- 单任务 4 轮代码生成后卡住 ⇒ **换目标**，而不是无限重试
- 失败任务**留在列表里**，以后可能重来
⇒ 这是**"停止条件的三个档"**的现成形态：**成功 / 局部放弃 / 全局预算**。
⇒ **省掉什么实验**：我们的停止条件可以直接抄这三档，避免出现"只报 max trials"的单一旋钮（我们 PROTOCOL 的 L1–L4 需要分层的停止规则）。

### 5.7 路线 B / C 的定位
- **路线 B**：Voyager **完全不训练**（"bypasses the need for model parameter access and explicit gradient-based training or finetuning"）⇒ 它是**纯 in-context 路线**，是路线 B 的对照靶子，不是先例。
- **路线 C**：它的"设计"部分（3 个模块的接口、8 个控制原语、prompt 结构）是人写的；"调参"部分只有 temperature 与 top-k。⇒ 它对应我们的 **L0 做得最好、L1–L4 全缺** 的状态。

## 6. ★ 不可迁移 / 会误导我们的点

1. **★ 它是"自我反思类"里最容易被我们误抄的一篇，因为它的组件名很像我们要的东西**（课程 / 技能库 / 迭代提示 / 自验证 / 反思）。但：
   - **它的所有"状态"都是 Minecraft 专属的结构化对象**（物品、坐标、程序）⇒ **它没有解决"自由文本里的信息维度"问题**，连问题都不是我们的
   - ⇒ **它的 3.3× / 15.3× / −73% 这些数字不能作为我们任何指标的预期值**
2. **★ 判官同源（坑 ⑥ 的极端形态）。** critic = 另一个 GPT-4 实例。整条流水线最关键的组件（−73%）是同源自评。⇒ **我们不能引用"Voyager 用自验证很成功"来支持"我们用判官量维度数"。** 这是"一个方法在**有环境真值**的场景里靠自验证成功"与"**没有环境真值**的场景里靠自评下结论"之间的差别。
3. **★ 没有重复实验、没有方差、没有 CI。** 3 次试验、160 iteration 就报 "3.3×"。⇒ 它的效应量**不可信到不能当先验**。
4. **★ 它的"多样性"是"发现了多少种不同物品"（外部可数），不是"输出里有多少个信息维度"。** ⇒ **不能拿它当"思维面"的操作化**。它的"unique items"≈ 我们的"承重维度数"吗？**不是**：物品是外部世界的可数实体，且**没有"这个物品改变了哪个决策"这一层**。⇒ 我们的"承重"是**决策影响**，Voyager 的"unique item"是**产出种数**。⇒ 这是我们与它的根本差别，也是我们 PROTOCOL §1.0 的"承重"问句**不能省**的原因。
5. **⚠️ 它的"新颖"是"没见过的物品"，由外部世界定义 ⇒ 天然不撞 embo-01。** 但它的**技能检索**用 embedding（相似度）⇒ 若我们抄"embedding 检索 + 去冗余"，就会把两种用途混用。**检索用相似度 OK；新颖/冗余判据必须用结构。**
6. **⚠️ 基线是"重新解释后的"基线**（作者自认）。"ReAct/Reflexion/AutoGPT 被我们改造到能在 MineDojo 跑" ⇒ **3.3× 里面有一部分是"基线被改造得不好"**。⇒ 引用倍数时要带上这个限定。
7. **⚠️ 幻觉会污染状态**：课程器会提不存在的物品（"copper sword"），代码生成会调用不存在的 API。⇒ **我们的依据包/状态生成环节同样会产出"不承重"的条目**（我们的 F3-a「花絮膨胀」就是 Voyager 的幻觉版）。
8. **⚠️ 成本只有相对值**（GPT-4 是 GPT-3.5 的 15×），**没有绝对美元数** ⇒ 我们的预算护栏拿不到基线。

## 8. 读完后我自己的一句判断

- **最值得抄的**：**"自动课程 = 看状态 + 失败列表 → 给目标，但不给解法"** 这条分工。它是**路线 A 里"目标生成"与"求解"必须分开**的现成证据，而且它的措辞是**中性**的（"previously completed and failed tasks"，不是"你上次错了"）——**这正是我们坑 ⑦ 要的措辞纪律**。把这条抄进路线 A 的 DESIGN，等于同时抄到了"目标生成"和"措辞中性"两件事。
- **最容易骗我们的**：**"自验证去掉 = −73%"这个数字太漂亮了，它会诱使我们把"判官"当成"思维面"的探测器**。但 Voyager 的判官判的是"**程序有没有达成一个外部可验证的物品/事件**"——**它有环境真值做锚**。我们的判官要判的是"**这一段话里的哪几条是承重的**"——**没有环境真值**。⇒ **同一个"自验证"名字，在两个问题里是两种东西**：一个是**执行检查**（客观），一个是**语义判定**（主观、会漂移）。如果我们在讨论里把 Voyager 的 −73% 当成"自验证值得投入"的证据，就会把"执行检查的可靠性"错当成"语义判定的可靠性"。⇒ **抄它的三档停止条件，不抄它的判官可信度。**

## 9. 附：任务书真正想要的 "Lost in the Middle"（arXiv 2307.03172）— **已读到正文**

**引用**：*Lost in the Middle: How Language Models Use Long Contexts*，Nelson F. Liu, Kevin Lin, John Hewitt, Ashwin Paranjape, Michele Bevilacqua, Fabio Petroni, Percy Liang（Stanford / UC Berkeley / Samaya AI），arXiv **2307.03172**，2023-07-06（v3），后发表于 **TACL**。
**取源**：`https://ar5iv.labs.arxiv.org/html/2307.03172`（150KB 完整 HTML，提取 670 行；读了 §1–§7 与附录 E 的可读部分）。⚠️ `export.arxiv.org/e-print/2307.03172` 在本会话中多次下载被截断（gzip EOF），故走 ar5iv 镜像。

**它声称解决什么**：受控地改变"相关信息在输入上下文里的**位置**"，看模型性能怎么变 ⇒ 结论是 **U 形曲线**（首因偏置 primacy bias + 近因偏置 recency bias，中间塌陷）。

**核心机制（可照着实现）**

| 项 | 内容 |
|---|---|
| **输入** | 两个任务：① **多文档 QA**：1 个问题 + k 个 Wikipedia 段落（≤100 token），**恰好 1 个含答案**，其余 k−1 个是干扰文档；② **合成 key-value 检索**：一堆 JSON 键值对（128-bit UUID），给定 key 返回 value |
| **状态表示** | 无状态。**操纵变量只有两个**：上下文长度（10/20/30 篇文档；75/140/300 对 key-value）与**相关信息的位置**（放最前 / 中间 / 最后，或扫描整个位置轴） |
| **动作/算子** | 只有一个：生成答案（exact match 评分） |
| **过程/回路** | 无迭代。**纯受控测量** |
| **输出** | 每个 (模型, 长度, 位置) 组合下的准确率 |
| **谁来评价** | ★ **纯外部 oracle**（NaturalQuestions-Open 的人工标注答案 / 精确匹配的 value）⇒ **零自评、零 embedding、零措辞相似度** |

**关键数字（逐字核对）**

- **Table 1（closed-book vs oracle）**：LongChat-13B(16K) **35.0% / 83.4%**；MPT-30B-Instruct **31.5% / 81.9%**；**GPT-3.5-Turbo 56.1% / 88.3%**；GPT-3.5-Turbo(16K) **56.0% / 88.6%**；Claude-1.3 **48.3% / 76.1%**；Claude-1.3(100K) **48.2% / 76.4%**
- **最刺眼的一条**：**"when relevant information is placed in the middle of its input context, GPT-3.5-Turbo's performance on the multi-document question task is lower than its performance when predicting without any documents (i.e., the closed-book setting; 56.1%)"** ⇒ **把文档放中间，不如不给文档**
- **"GPT-3.5-Turbo's multi-document QA performance can drop by more than 20%"**；在 20/30 文档设置下，**最差位置低于 closed-book**
- **长上下文 ≠ 用得上上下文**："the 10- and 20-document settings both fit in the context window of GPT-3.5-Turbo and GPT-3.5-Turbo (16K), and we observe that their performance … is nearly superimposed" ⇒ **扩展上下文窗口不改善位置鲁棒性**
- **query-aware contextualization**（把 query 放文档**前后**）在 key-value 上 "all models achieve near-perfect performance on the 75, 140, and 300 key-value pair settings"；但在 multi-document QA 上 "minimally changes trends"
- **指令微调不是原因**："Both models have a U-shaped performance curve… indicating that the instruction fine-tuning process itself is not necessarily responsible for these performance trends"；MPT-30B vs Instruct 相比，"the instruction fine-tuning slightly reduces the worst-case performance disparity from **nearly 10%** between the base model best- and worst-case performance to **around 4%**"
- **规模门槛**：Llama-2 **7B 纯 recency 偏置（无 primacy）**，**13B / 70B 才出现 U 形**；作者推测以前文献没看到 primacy bias 是因为模型 <1B
- **GPT-4 也有 U 形**（附录，500 个样本 × 20 文档）："GPT-4 achieves higher absolute performance than any other language model, but still shows a U-shaped performance curve"
- **检索侧案例**："reader model performance saturates long before retriever performance saturates"；"Using more than 20 retrieved documents only marginally improves reader performance (**~1.5% for GPT-3.5-Turbo and ~1% for Claude-1.3**), while significantly increasing the input context length (and thus latency and cost)"

**★ 它提出的"新的评估协议"（对我们最有用的一句）**

> "to claim that a language model can robustly use information within long input contexts, it is necessary to show that its performance is **minimally affected by the position of the relevant information** in the input context (e.g., **minimal difference in best- and worst-case performance**)."

⇒ ★★ **这正是我们坑 ④（测量带宽 > 信号带宽）的操作化版本**：我们的判官读数，如果只是"一个读数"，我们无法知道它稳不稳；**要证明我们的 VD 读数可信，必须报"最好情况 − 最坏情况"的差**（把同样内容、不同顺序/位置的依据包重跑）。

⇒ 抄法：**把"依据包的顺序/位置"当作我们测量协议的一个必需控制变量**，并把 **worst-case − best-case 差**作为**读数的带宽指标**报出来（而不是只报均值）。

⇒ ★ 这与我们 PROTOCOL 里"跨判官提示词版本漂移"是**同一族**的带宽概念（换了个轴：位置/顺序 vs 提示词版本）——**两个轴合起来才是我们真正的测量带宽**。

**不可迁移 / 会误导我们的点**

1. **它的量纲是"位置 → 准确率"，我们的量纲是"维度数 → 决策改变"** ⇒ 它的 U 形曲线**不能**直接推出"我们的维度计数会随位置漂移"。但它提供的是**"位置是一个真实的隐藏混淆变量"这个一般性证据** ⇒ 对我们：判官提示词里的**依据包顺序**必须被当作**已知的隐藏变量**控制住。
2. **它不涉及自我反思/迭代**，没有"这次比上次好"的机制 ⇒ 与本组其他五篇**不同构**，只能当"测量学"参考。
3. **没有位置曲线的置信带/CI** ⇒ 它的"掉 20%"没有带宽标注。
4. **别把它读成"长上下文没用"**：它的结论是"**长上下文里**的信息**位置**有偏置"，不是"上下文长度本身有害"。**它的 20 文档设置恰恰是"更多上下文"的设置** ⇒ 它同时证明了"更多上下文 ⇒ 表现可能更差"（因为干扰文档也进上下文）——**这与文件 18 的"约束优化"结论同向**。
